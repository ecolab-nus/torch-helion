Pipeline

Loom compiles a single kernel with one parallel grid and one reduction loop. torch-helion's job is to reach that shape from a whole model: capture it, normalise the graph until only Loom's registered operators remain, decide where the kernel boundaries go, and emit each kernel exactly the way Loom's frontend expects. Each arrow below writes a file under results/<run>/.

OpGraph

An OpGraph is an ordered DAG in which every node produces exactly one tensor with a concrete shape and dtype. It is built literally from the exported ATen graph, then rewritten by the optimizer until it contains only operators the hardware spec knows, plus two macro nodes (row_sumsq, attention) that map onto kernel templates.

What a pass does to the graph

RMSNorm is the pass with the most algebra. In the raw graph it is six elementwise nodes ending in a per-feature gain, and its output feeds three GEMMs. The lowering commutes the row scale through the GEMMs, folds the gain into each weight, and leaves the sum of squares as a reduction over the GEMM's own K axis, where the kernel can accumulate it in the same loop.

Optimizer passes

The passes run in a fixed order and each one is checked numerically: the graph is re-evaluated after every pass and compared with the raw graph. Rewrite counts and drift from the llama_block run:

#passeffectrewritesnodes aftermax rel err
After canonicalisation every activation is a token-major 2D tensor, every weight is a [K, N] constant, and the only non-registered nodes are row_sumsq and attention. That is the contract the partitioner relies on.

Partition and plan

Kernels are anchored by reductions: a group of GEMMs sharing their LHS, or one attention op. Everything else is pulled into the epilogue of the kernel that owns its inputs; values that cross a kernel boundary become DRAM tensors. The only structural freedom is which sibling GEMMs share a kernel, so the planner enumerates set partitions of every sibling group, checks legality, and costs each candidate.

OpIR

The OpIR is a Program: an ordered list of KernelSpecs plus a tensor table. A kernel spec is a complete description of one Helion kernel; codegen renders it without further analysis and the interpreter executes it with plain PyTorch.

Cost model vs Loom

  
The planner uses an analytic estimator that mirrors Loom's ETG aggregation with the per-function costs from the hardware perf YAMLs: per grid tile, the loop runs iters × max(load, compute) when double buffering fits in L1, plus epilogue and stores, times the number of waves over the 64-core mesh. After planning, every kernel was also pushed through Loom's full pipeline (frontend, exploration, ETG resolution, CP-SAT solve, materialisation).

Loom kernel contract

  
The README lists six architectural constraints (one grid, one loop-carried loop, shared loops for shared kernels, registered ops only, 32-aligned rank-2 operands, constexpr scalars). Making real kernels pass Loom's exploration exposed six more rules; the emitter encodes all of them.
